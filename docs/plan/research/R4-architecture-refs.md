FlexMeasures pins the primary-key column order deliberately (lines 1033-1068): `(sensor_id, source_id, event_start, belief_horizon, cumulative_probability)` with the reasoning quoted in the docstring: "sensor_id first, because virtually every query filters on a single sensor", "cumulative_probability last, because it is very nearly a constant (0.5 for every deterministic belief)". - flexmeasures/data/models/data_sources.py
  - `DataSource` (lines 436-490): `type` String(80) (user, forecaster, scheduler, reporter...), `user_id` unique nullable, `account_id` nullable, `attributes` JSONB plus `attributes_hash` LargeBinary(256) (lines 478-480) so that one DataSource row identifies one exact (model, version, config) combination, `model` String(80), `version`. Lines 709-775: a priority order among sources resolves which belief wins when several sources report the same event.
  - `SensorDataSource` (lines 382-411): an explicit (sensor_id, source_id) pair table so "which sources have data for this sensor" is a cheap lookup instead of a scan of timed_belief.

Belief semantics (documentation/concepts/time-series-and-beliefs.rst and timely_beliefs/docs/timing.md, fetched 6 Nov 2026):

- "For every time-series value, FlexMeasures records both when the event happens and when that value became known or was asserted."
- `belief_horizon = knowledge_time - belief_time`; for a physical event `knowledge_time = event_end`, so "a positive horizon describes a belief made before the event was fully known, while a negative horizon describes an ex post belief made after it."
- Timing docs: "Beliefs about past events can be modelled using a negative horizon"; `knowledge_horizon` "says how long before (the event starts) the event could be known" and "equals -resolution for physical events".
- Query filters `prior` (belief_time <= prior) and `horizon` (belief_horizon >= horizon) select "what was known at time X". The schedule GET endpoint reads with `most_recent_beliefs_only=True, one_deterministic_belief_per_event=True` (sensors.py lines 1402-1408).
- Ingestion floors off-clock timestamps to the sensor resolution by default (`floor_datetimes_to_resolution` attribute) - relevant to 1-minute telemetry from inverters with drifting clocks.

Why this matters for the OnyxLeaf service: savings verification by counterfactual replay and switchback A/B is only honest if the service can reconstruct "what the optimiser knew at 06:00" (the PV and load forecasts and outage probabilities it solved on) separately from "what actually happened" (ex post telemetry) for the same 15-minute event. A belief timestamp on every forecast and plan row gives that for free; a plain (time, value) table does not. It also makes forecast-skill scoring per horizon a query rather than a side system.

What to adopt:

1. Tables `account` (tenant; theming columns; parent "consultancy"/installer account for the white-label installer portal), `user` (account_id NOT NULL, roles), `asset` (tree with parent_asset_id; type; lat/lon; `attributes` JSONB; `external_id` for the Product 2 device id or OEM-cloud plant id), `sensor` (asset_id, name unique per asset, unit, event_resolution, timezone), `data_source` (type, model, version, attributes_hash), `timed_belief` (sensor_id, source_id, event_start, belief_horizon, cumulative_probability, event_value) with the FlexMeasures PK order.
2. Keep `cumulative_probability` even if only 0.5 is written at first: PV/load quantile forecasts (P10/P50/P90) and outage probability fit the same row shape without a schema change.
3. Store `flex_model` and `flex_context` style site configuration as JSONB on the site asset: the battery model (usable kWh, power limits, efficiencies, min/max SoC, throughput cost) and the context (tariff id, export cap, genset curve, critical load) are per-site and change rarely; JSONB with a pydantic schema, as FlexMeasures does with marshmallow, avoids a wide table per device class.

What to simplify: OnyxLeaf does not need generic "any commodity" flexibility (heat, gas, steam coupling groups, S2 operation-mode bands) that FlexMeasures v1 added; one electricity commodity with a fixed set of device kinds (pv, battery, grid, genset, load) keeps the model readable.

### 1.2 Scheduling job pattern (adopt the shape, use the same queue library)

Source: flexmeasures/data/services/scheduling.py; flexmeasures/data/services/utils.py; flexmeasures/data/services/job_map.py; flexmeasures/utils/config_defaults.py.

- RQ on Redis, one queue per job kind (`current_app.queues["scheduling"]`, `["forecasting"]`, and an ingestion queue). Config defaults (config_defaults.py lines 164-188): `FLEXMEASURES_LP_SOLVER = "highspy"`, `FLEXMEASURES_DEFAULT_JOB_TIMEOUT = 180 s`, `FLEXMEASURES_JOB_TTL = 1 day`, `FLEXMEASURES_PLANNING_HORIZON = 2 days`, `FLEXMEASURES_MAX_PLANNING_HORIZON = 2520` steps, `FLEXMEASURES_PLANNING_TTL = 7 days` (job result retention), `FLEXMEASURES_JOB_CACHE_TTL = 3600 s`, Redis URL/port/db/password.
- `create_scheduling_job` (scheduling.py lines 222-357) validates the flex config synchronously before enqueueing ("so users get a meaningful response right away", lines 269-290), creates the RQ `Job` with `on_failure=Callback(trigger_optional_fallback)`, `on_success=success_callback`, `depends_on` (lines 292-317), serialises start/end/resolution/belief_time into `job.meta["scheduler_kwargs"]` as ISO strings (lines 324-341, a workaround for rq-dashboard issue 510), and registers the job id in a per-asset Redis index (`current_app.job_map.add`, lines 353-357).
- `@job_cache("scheduling")` (utils.py lines 323-375): hashes the call arguments into a Redis key `queue:func:hash -> job_id`, takes a Redis lock on that hash "so that concurrent calls with the same arguments share one job, rather than each missing the cache and creating their own" (lines 354-361). This is the de-duplication that keeps a 15-minute re-solve loop plus user-triggered re-solves from double-solving.
- `JobMap` (job_map.py lines 22-60): Redis sets keyed `scheduling:asset:<id>` so the API can list jobs per asset and paginate without scanning RQ registries.
- `make_schedule` (scheduling.py lines 959-1180) is the worker function: `db.engine.dispose()` first (fork safety, line 988), re-instantiates the scheduler class from a serialisable spec, stores `scheduler.info` and `data_source_info` in `rq_job.meta` so the API can look results up (lines 1083-1087), raises `InfeasibleProblemException` through to the failure callback, and writes results as `TimedBelief` rows with `belief_time` = the job's belief time and source = the scheduler's own `DataSource` (one row per (model, version, config hash)).
- Failure path: `trigger_optional_fallback` (lines 145-219) enqueues a fallback job only if `scheduler_class.fallback_scheduler_class` is set, and links the two jobs through `job.meta["fallback_job_id"]` / `fallback_job.meta["original_job_id"]`. Important change in the current changelog (documentation/changelog.rst lines 319-327, v1.1.0 block): "The built-in storage fallback scheduler has been retired: an infeasible storage problem now fails with its failure reason instead of silently saving a fallback schedule. We expect a fallback to be needed much less than before: in practice, it was mostly infeasible SoC minima and maxima that triggered it, and those preferences are now relaxed by default". A grep for `fallback_scheduler_class` finds no assignment anywhere outside the base class at this commit.
- Recurring work: flexmeasures/data/models/automations.py (389 lines) and `flexmeasures jobs run-automations` (flexmeasures/cli/jobs.py lines 88-135) claim "durable automation run records" per scheduled run so that a cron tick that queues N jobs is resumable and idempotent. Worker stats via Little's law (`jobs stats`, lines 198-235).
- Ingestion is also a job: `process_sensor_data_ingestion` (flexmeasures/api/common/utils/api_utils.py lines 138-180): "If an ingestion queue with connected workers is available, enqueue a background job and return 202 Accepted. If no worker is available, process the data synchronously"; the ingestion job then enqueues forecasting jobs only "upon successfully saving new data" (data_ingestion.py lines 153-215).

What to adopt for the OnyxLeaf backend (FastAPI): the same four-queue design (ingest, forecast, optimise, report) on RQ + Redis (RQ is BSD-licensed, pure Python, runs on Windows via rq-win for dev), the argument-hash job cache with a Redis lock, a per-site job index, `on_failure`/`on_success` callbacks, job meta holding the solver info and the result's data_source id, and a durable "scheduled run" table for the 15-minute tick (so a worker restart re-claims rather than re-runs). Validate the site config synchronously at trigger time, exactly as FlexMeasures does, so the API returns 422 immediately on a bad battery model instead of a failed job 30 s later.

### 1.4 StorageScheduler (read for the formulation; copy the soft-constraint idea, not the generic engine)

Source: flexmeasures/data/models/planning/storage.py (4,237 lines), linear_optimization.py (848), highspy_optimization.py (771), scheduling_problem.py (843), soc_projection.py (489), devices.py (822), __init__.py (860).

- Two interchangeable solver backends build the same model: Pyomo (`device_scheduler`, linear_optimization.py line 122, `SolverFactory(current_app.config["FLEXMEASURES_LP_SOLVER"])` at lines 795-797, typically `appsi_highs`) and a direct highspy build (`device_scheduler_highspy`, highspy_optimization.py). The module docstring explains why: "bypassing the Pyomo layer cuts roughly a second (single device) to several seconds (multiple devices) of model construction and solution-ingestion overhead per scheduling job, while the direct build takes milliseconds", at the cost of "TWO MODELS TO KEEP IN SYNC" with an equivalence test suite (tests/test_highspy_equivalence.py). Default is the direct highspy path (config line 164).
- Variables (linear_optimization.py lines 479-504, 690, 744): `ems_power[d, j]` (Reals, net flow per device d per step j), `device_power_down[d, j]` and `device_power_up[d, j]` (NonNegativeReals) with `device_power_sign[d, j]` (Binary) so that charging and discharging cannot happen in the same step, `group_stock[sg, j]` (stock = SoC in MWh per stock group, so several devices can share one battery), `commitment_downwards_deviation[c]` / `commitment_upwards_deviation[c]` (NonNegativeReals) and `commitment_sign[c]` (Binary), `coupling_alpha` for hard flow coupling (CHP-style), `device_band[db, j]` binaries for S2 operation-mode bands.
- Device constraint columns (docstring lines 143-153): `max`, `min`, `equal` (stock), `efficiency` (stock left at the next step), `derivative max`, `derivative min`, `derivative equals` (flow), `derivative down efficiency`, `derivative up efficiency`, `stock delta` (a fixed inflow/outflow such as an inflexible load applied to the stock). EMS constraints: `derivative max`/`derivative min` on the summed flow (site import/export cap), per commodity group.
- Objective (lines 780-792): minimise the sum over commitments of deviation times price. Everything is a "commitment" (`Commitment`, `FlowCommitment`, `StockCommitment` dataclasses, planning/__init__.py lines 561-860) with a `quantity`, an `upwards_deviation_price` and a `downwards_deviation_price` series: a consumption price is a flow commitment of quantity 0 with an upward price; a contracted capacity is a commitment whose breach price is the penalty; a SoC minimum is a stock commitment with a downward price. This one abstraction is what lets the same LP express tariffs, export prices, demand charges, SoC targets and soft limits.
- Soft constraints and infeasibility avoidance (storage.py): `relax-constraints` defaults to True (lines 2133-2137: "leaves relaxation to the general relax-constraints flag (which defaults to True)"). When set, `soc-minima`, `soc-maxima` and `soc-targets` become stock commitments priced with `soc_minima_breach_price` / `soc_maxima_breach_price` from the flex-context (lines 1288-1440), and the hard constraints are removed ("soc-minima will become a soft constraint (modelled as stock commitments), so remove hard constraint", line 1351). Capacity limits get "any breach" and "all breaches" commitments (lines 651-760): one commitment priced on the single worst breach (a peak/demand-charge shape, MDI in Pakistan) and one priced on every breach (an energy-penalty shape). The physical power capacity stays hard; the contracted one is soft (lines 767-778). After solving, `_compute_unresolved_targets` (lines 2938-3129) reports which SoC targets/minima/maxima were not met ("unresolved") and which were met only through relaxation ("resolved"), returned in the job result and the jobs API. `prefer_charging_sooner` / `prefer_curtailing_later` (lines 945-972) add a "tiny price slope" so that ties are broken deterministically instead of leaving the solver to pick an arbitrary charging time.
- Off-tick SoC targets (soc_projection.py; storage.py lines 2078-2110): a target at 16:07 on a 15-minute grid is projected onto the tick and relaxation is auto-enabled for that device only, with a logged explanation.
- `compute()` (storage.py lines 3438-3482): builds initial stock per stock group, calls `device_scheduler`, and `if "infeasible" in termination_condition: raise InfeasibleProblemException(tc)`.
- Versioning: `StorageScheduler.__version__ = "9"`, `__author__ = "Seita"` (lines 2742-2744); the version is part of the DataSource identity so that schedules from an older model version are distinguishable in the database.

Adopt (re-implemented in the OnyxLeaf optimiser, not copied wholesale): the commitment/deviation-price formulation as the single objective abstraction; soft SoC floor before a predicted outage priced at the value of lost load rather than a hard constraint (hard reserve constraints are the number-one cause of infeasibility when the forecast and the battery state disagree); the "any breach"/"all breaches" pair for MDI and contracted-capacity charges; the "unresolved/resolved" post-solve report shown to the user ("reserve target for 19:00 could not be met, best achievable 42%"); a tie-breaking slope; a model `__version__` stamped on every plan row; the binary charge/discharge sign only where needed (it is what turns the LP into a MILP; genset on/off binaries are needed anyway). Build directly on scipy.optimize.milp / highspy rather than Pyomo for the same speed reason FlexMeasures gives, but do not maintain two backends: one direct HiGHS build plus a property-based test suite.

Reject: the generic multi-commodity device_scheduler itself (coupling groups, balance groups, operation-mode bands, shared stock groups across devices). It is 2,500+ lines of generality that a PV + battery + grid + genset site does not need, and it has no genset fuel curve, no min-up/min-down time, no outage window (grid import forced to zero), none of which fit the "commitment" abstraction without new variables.

### 3.1 Controller priority chain (adopt the idea for Product 2's rule layer and the cloud's "who may override whom")

Source: doc/modules/ROOT/pages/edge/architecture.adoc (sections "Controller", "Scheduler", "Cycle", "Process Image"); io.openems.edge.scheduler.api/src/io/openems/edge/scheduler/api/Scheduler.java; io.openems.edge.scheduler.allalphabetically/.../SchedulerAllAlphabeticallyImpl.java.

- The edge runs an input-process-output cycle "once per second" on a frozen "process image" ("This process image is guaranteed to never change during the cycle").
- "Controllers ... hold the actual business logic"; each "carr[ies] out only one specific, encapsulated task." `Scheduler.getControllers()` "Returns Component-IDs of Controllers ordered by their current execution priority ... called once every Cycle" (Scheduler.java javadoc). `SchedulerAllAlphabetically` returns the configured `controllers_ids` first, then every other enabled controller sorted by id (lines 40-56 of the impl).
- "Later executed Controllers are not allowed to overwrite a previously written result." The worked example in architecture.adoc: ESS limits allow +/-50 kW; `Ess.LimitTotalDischarge` (higher priority) forces a charge of at least 5 kW; the Balancing controller then asks for 20 kW discharge "but is forced to fulfil the constraints. Eventually the ESS gets force-charged with 5 kW." Setpoints are resolved by an `Ess.Power` component that "manages feasible solutions via a linear equation system".
- Important consequence stated in the doc: "Even northbound connections to a backend server or SCADA system and alike are implemented as Controllers. This assures for any setpoint request by an external system being embedded in the local prioritization system and naturally restricted by higher-priority controllers. Example: An external request to discharge the battery will be limited by the Ess.LimitTotalDischarge controller just like any other internal control algorithm."
- `Controller.Ess.LimitTotalDischarge` (io.openems.edge.controller.ess.limittotaldischarge/.../Config.java lines 26-33): `minSoc` default 15% ("Discharging is blocked while State of Charge is below Min-SoC"), `forceChargeSoc` default 10% ("Charging is forced while State of Charge is below Force-Charge-SoC"), `forceChargePower`; a three-state machine NORMAL / MIN_SOC / FORCE_CHARGE_SOC with a hysteresis in minutes (impl lines 13-130); `forceChargeSoc` is clamped to `minSoc - 1` if misconfigured (lines 59-63).

Adopt (as design): the cloud plan is just one more "controller" at the edge, and it sits below the safety controllers. Product 2's rule layer should be an ordered list (1) battery protection (min SoC, force-charge, temperature derate), (2) reserve-for-outage floor, (3) genset interlocks, (4) the cloud plan step, (5) default self-consumption - with the rule that a lower item may only narrow the feasible setpoint range, never widen it. On the cloud side, mirror the same ordering in the optimiser as hard constraints (1, 3) and soft commitments (2) so that a plan is never produced that the edge would refuse.

Reject: the genetic search itself (non-deterministic, no optimality gap, "TODO" on horizon quality in GocUtils), the six-hour quarter / hourly tail split as a hard-coded function of the clock, and the one-second edge loop as a cloud design (the cloud re-solves at 15 minutes; the per-second loop belongs to Product 2).

### 3.3 Emergency capacity reserve controller (adopt the hysteresis ladder for the outage reserve)

Source: io.openems.edge.controller.ess.emergencycapacityreserve/src/io/openems/edge/controller/ess/emergencycapacityreserve/ (ControllerEssEmergencyCapacityReserveImpl.java 200 lines, statemachine/StateMachine.java, statemachine/*Handler.java, statemachine/Context.java, EnergyScheduler.java, Config.java).

- Config: `reserveSoc` (percent) and `isReserveSocEnabled` (Config.java lines 23-27); the impl warns if the reserve is outside 5..100% (`reservSocMinValue = 5`, `reservSocMaxValue = 100`, lines 44-46, 125-131).
- States (StateMachine.java lines 9-35, with their javadoc): `UNDEFINED(-1)` ("Start state for new StateMachine, never entered again"), `NO_LIMIT(1)` ("SoC is greater then configured reserve SoC"), `ABOVE_RESERVE_SOC(2)` ("SoC is 1% above configured reserve SoC"), `AT_RESERVE_SOC(3)` ("SoC equals to the configured reserve SoC"), `BELOW_RESERVE_SOC(4)` ("SoC is under configured reserve SoC"), `FORCE_CHARGE_PV(5)` ("SoC is 1% under configured reserve SoC"), `FORCE_CHARGE_GRID(6)` ("SoC is 2 % under configured reserve SoC").
- Transitions and setpoints (the handlers): NO_LIMIT sets target power = max apparent power (no constraint), ramp 1%/cycle, goes to ABOVE_RESERVE_SOC when soc <= reserve + 1. ABOVE_RESERVE_SOC allows discharge up to max(maxApparentPower/2, DC PV production), goes to AT_RESERVE_SOC when soc <= reserve, back to NO_LIMIT when soc > reserve + 1. AT_RESERVE_SOC allows discharge only up to the DC PV production (so the battery may pass PV through but not drain), goes BELOW when soc < reserve, ABOVE when soc > reserve + (1 if the last active state was FORCE_CHARGE_GRID else 0) - a one-percent hysteresis after a grid charge. BELOW_RESERVE_SOC sets target 0 (no discharge), ramp 5%, goes to FORCE_CHARGE_GRID if soc <= reserve - 2 and grid charging is allowed (`meta.getIsEssChargeFromGridAllowed()`), FORCE_CHARGE_PV if soc <= reserve - 1 or soc <= 0. FORCE_CHARGE_PV charges with the AC PV production, returns to AT_RESERVE_SOC when soc >= reserve + 1 or 100. FORCE_CHARGE_GRID charges at 50% of max apparent power if soc <= reserve - 4 (or <= 0) else 10%, leaves when grid charging is disabled or soc >= reserve + 1.
- The setpoint is applied as `ess.setActivePowerLessOrEquals(rampFiltered)` (impl lines 103-112): the reserve controller only caps discharge, it never sets the power itself, which is what lets it sit above the TOU controller in the priority chain without fighting it. If SoC is undefined the last valid SoC from the channel history is used; if there is none, or max apparent power is undefined, the machine is forced to NO_LIMIT (lines 150-162) - the controller fails open, not closed, because a stuck "no discharge" would be worse than a lost reserve.
- Link to the optimiser (EnergyScheduler.java in the same bundle, lines 1-20): the reserve enters the schedule simulation as a one-mode handler that sets `ef.setEssLessOrEquals(max(0, initialEnergy - minEnergy))`, that is, the reserve is a hard lower bound on energy in the simulated horizon, with `minSoc` serialised into the schedule context.

Adopt: the exact ladder (NO_LIMIT / ABOVE / AT / BELOW / FORCE_CHARGE_PV / FORCE_CHARGE_GRID) with 1-2% hysteresis bands and ramped power for Product 2's reserve rule, with the reserve level itself being a time-varying number sent by the cloud plan (the outage-probability-weighted reserve for the next hours) instead of a static percent; "fail open" on undefined SoC but with an alarm; "grid charging allowed" as a site-level flag the tariff engine can switch by TOU period. In the MILP, model the reserve as a soft stock commitment (section 1.4) and send the resulting per-step reserve floor as the `reserve_soc` field of the plan step.

### 3.4 Grid-optimized charge (reference for a "delay PV charging to avoid curtailment" mode)

Source: io.openems.edge.controller.ess.gridoptimizedcharge/.../Config.java, DelayChargeRiskLevel.java. Config: `maximumSellToGridPower` default 7000 W (line 32, deprecated in favour of a Meta grid feed-in limit), `delayChargeRiskLevel` LOW | MEDIUM | HIGH (line 35: "Low Risk: More often 100% SoC but more PV-curtails possible - High Risk: More PV-curtails avoided but less weight on the SoC"), `mode` AUTOMATIC | MANUAL | OFF, `manualTargetTime` default "17:00" ("Charging to 100 % SoC is delayed till this hour of the day"), `sellToGridLimitRampPercentage` default 2. Relevant to Pakistan only where an export cap exists (net-billing sites with a sanctioned export limit); the "target full by time T with a risk-level buffer" idea maps directly to "reserve full before the evening shedding window with a buffer that depends on forecast confidence".

### 3.5 Edge/Backend split and behaviour when the backend is unreachable (adopt the design)

Source: doc/modules/ROOT/pages/backend/architecture.adoc; io.openems.edge.controller.api.backend/src/io/openems/edge/controller/api/backend/ (Config.java, ControllerApiBackendImpl.java 318 lines, WebsocketClient.java, OnError.java, SendChannelValuesWorker.java 449, ResendHistoricDataWorker.java 252, services/BackendConnectionStateListenerImpl.java); io.openems.common ClientReconnectorWorker.java (fetched from raw.githubusercontent.com on 6 Nov 2026, not in the sparse checkout).

- Topology (backend/architecture.adoc): "An OpenEMS Edge connects to the Backend using its Controller.Api.Backend over a WebSocket connection." The edge-facing endpoint was split into a separately deployable "Backend.Edge.App" that "accepts the incoming WebSocket connections from the Edges (authenticating each Edge by its API-key)", "relays messages in both directions", and "keeps a local cache of connection state (e.g. the mapping of API-key to Edge-ID)"; the central backend holds Edge.Manager, Metadata (identification and authorisation of edges and users), Timedata (persistence and query of historic data) and Ui.Websocket. "the Edge Controller.Api.Backend does not need to be modified: an Edge always connects to a Backend.Edge.App, regardless of how many Edge-facing servers are deployed."
- Edge config (Config.java lines 26-60): `apikey` (type PASSWORD), `uri`, proxy settings, `apiTimeout` default 60 s ("the timeout in seconds for updates on Channels set by this Api" - a setpoint written by the backend expires after 60 s if not refreshed), `persistencePriority` HIGH (which channels are sent every cycle), `aggregationPriority` LOW (which channels are sent as 5-minute aggregates), `resendPriority` HIGH (which channels are re-sent after an outage, "Should match with the persistence priority configured in your timedata"), feature flags `DATA_PROVIDER`, `UPLOAD_CHANNEL_DATA`. The impl warns when the URI scheme is not https/wss: "This may lead to credential exposure. Do not use this configuration in production!" (lines 90-95). Each edge sends an `INSTANCE_ID` header on the handshake (lines 85-88, WebsocketClient.java lines 36-41).
- Data upload (SendChannelValuesWorker.java): per-cycle values are queued in an `ArrayBlockingQueue(1)` (line 65: only the latest cycle is kept while the link is slow) and 5-minute aggregates (`AGGREGATION_MINUTES = 5`, line 58) are scheduled with a random offset of up to 90% of the window (line 73, to spread fleet load on the backend); a full snapshot of all channels is re-sent on config change and periodically (`sendValuesOfAllChannelsOnce`, lines 100-108).
- Disconnect and reconnect: on close the edge logs "Disconnected from OpenEMS Backend" and sets an `UNABLE_TO_SEND` channel to true (WebsocketClient.java lines 18-28); OnError.java only logs. The reconnector (ClientReconnectorWorker) runs a 1-second cycle (`THREAD_CYCLE_MILLIS = 1_000`), with `DEFAULT_CONFIG` `connectTimeoutSeconds = 100`, `minWaitSeconds = 10`, `maxWaitSeconds = 100`: each worker picks one random wait between 10 and 100 s at construction and retries at that fixed interval, no exponential backoff (random per edge so a fleet does not reconnect in lock-step after a backend restart). `BackendConnectionStateListenerImpl` publishes `StillInitializing` for the first 100 s (`initializeTime = Timeout.ofSeconds(100)`), then `Connected` or `NoConnection(elapsed)` with a stopwatch of how long the link has been down, and a `DataFetchType` that other components can observe.
- Resend after an outage (ResendHistoricDataWorker.java lines 20-110): the worker starts only after an explicit trigger plus `DELAY_TRIGGER_TIME = 300_000 ms` (5 minutes after reconnect), with a random extra delay up to `MAX_RANDOM_DELAY = 3_600_000 ms` (1 h), reads `getResendTimeranges(addressForSuccessfulSend, latestResendTimestamp)` from the local Timedata (the edge keeps its own time-series store), adds `BUFFER_SECONDS = 300` on each side, and resends in chunks of at most `MAX_RESEND_TIMESPAN_SECONDS = 300` (5 minutes of data per message), advancing `LAST_SUCCESSFUL_RESEND` only when the backend acknowledges; "if data can not be send wait for next trigger".
- Control while offline: the TOU controller keeps the last schedule and keeps executing it (the schedule lives in the EnergyScheduleHandler on the edge; `Optimizer` runs on the edge, not in the backend), and with no schedule at all it falls back to BALANCING with no setpoint (Utils.java lines 76-78; the debug log prints "|No Schedule available", Impl line 196). In OpenEMS the optimiser is on the edge, so backend loss only loses tariff/prediction refresh and monitoring; the forecasts and prices are fetched by the edge itself. OnyxLeaf's design puts the optimiser in the cloud, so the equivalent protection must be: the edge holds the full 48-hour plan with `valid_until`, executes the current step, and reverts to the inverter's own mode when the plan expires (as the Product 1 report already states; Victron Dynamic ESS documents a 12-hour revert; Schneider Microgrid Advisor a 48-hour local fallback).

Adopt for the cloud service: an edge-facing gateway service separate from the API/UI service (the Backend.Edge.App split), authenticating each Product 2 device by API key + instance id over WSS or MQTT-over-TLS; per-channel upload priorities (1-minute live values for a small set, 5-minute aggregates for the rest) with a random phase offset per site; an explicit connection-state model per site (initialising / connected / no-connection since T) surfaced on the fleet page and used by the optimiser (a site that has been offline for more than N minutes is re-planned with stale-state penalties or not at all); a resend protocol driven by "last acknowledged timestamp" per channel with bounded chunk size and a randomised start delay; a setpoint TTL (`apiTimeout`) so any value the cloud writes expires on the edge if not refreshed; alarms for `UNABLE_TO_SEND`. The plan payload must carry `valid_from`, `valid_until`, per-step reserve floor and the "safe default" so the edge can act alone for the whole horizon.

## 6. Concrete schema and interface sketch distilled from the three references

Tables (Postgres): `account`, `account_role`, `user`, `role`, `plan` (commercial plan), `asset_type`, `asset` (site, inverter, battery, genset, meter, pv_array; parent_asset_id), `sensor`, `data_source`, `timed_belief`, `annotation` (outage, genset_run, maintenance, holiday), `site_config` (JSONB flex_model/flex_context with version), `tariff` + `tariff_period` (Pakistan TOU calendars, seasonal, by DISCO and category), `job_run` (durable scheduled runs), `plan` (site_id, generated_at, belief_time, valid_from, valid_until, model_version, data_source_id, status, reason, objective_value, inputs_ref, unresolved JSONB), `plan_step` (plan_id, step_start, state, battery_kw, grid_import_cap_kw, export_cap_kw, reserve_soc, genset_on, tou_slot_payload JSONB, cost_breakdown JSONB), `device_connection_state` (site_id, state, since, last_ack_ts per channel), `audit_log`.

Queues (RQ on Redis): `ingest`, `forecast`, `optimise`, `report`; job cache keyed by (site_id, belief_time rounded to the 15-minute tick, config hash).

API (FastAPI, `/api/v1`): `POST /sensors/{id}/data` (compact series, 202), `GET /sensors/{id}/data?prior=&horizon=&source=`, `GET /sensors/{id}/status`, `POST /sites/{id}/plans/trigger` -> 202 `{job, job_url, results_url}`, `GET /sites/{id}/plans/{job}` (202 while running, 200 with steps), `GET /sites/{id}/plans/current` (active plan with `get_active_step(now)` semantics), `GET /jobs/{id}` (status, unresolved/resolved), `GET /sites/{id}/kpis?start&end`, `POST /sites/{id}/annotations`, `GET /sites/{id}/connection`, `PUT /sites/{id}/config/{path}` with backup/revert, `GET /forecasts/providers`, `PUT /forecasts/import/{provider_id}`, `GET /forecasts/series?key=&start=&end=&interval=&fill=&resample=`. Edge gateway (separate process): WSS/MQTT with API key + instance id; messages `telemetry` (1-minute live set), `aggregates` (5-minute), `resend` (chunked by last ack), `plan` (push on new plan; TTL), `applied_state` (edge reports what it did), `heartbeat`.

Plan state machine (per site): `idle` -> `reoptimising_current` | `optimising_future` -> `optimised` -> (next tick or event) ; `failed(reason)` keeps the previous `optimised` plan active until `valid_until`.

Offline rule (edge, Product 2): execute the current plan step while `now < valid_until` and the safety ladder allows it; on expiry or stale telemetry revert to the inverter's own mode with the last reserve floor; on reconnect, resend telemetry since last ack, then fetch the current plan.

## 7. Open questions (UNVERIFIED or not settled by the sources)

1. timely-beliefs as a dependency vs. own `timed_belief` table: the mixins target SQLAlchemy and pandas BeliefsDataFrame; with pandas 3.0 in the ops env their compatibility was not tested here (UNVERIFIED). A plain own table with the same five-column key is the low-risk route.
2. RQ on Windows for development needs rq-win (FlexMeasures lists `rq-win; os_name == 'nt'`); production on Linux. Not tested in this run.
3. FlexMeasures' per-plan rate limits (`trigger_rate_limit`) rely on Flask-Limiter; the FastAPI equivalent (slowapi or a Redis token bucket) was not evaluated.
4. The OpenEMS quarter/hour split and the `EFFICIENCY_FACTOR = 1.17` are heuristics specific to FENECON hardware; they are cited for context, not adopted.
5. The OpenEMS UI (AGPL) was not opened, so the "plan visualisation" patterns the guideline attributes to Predbat and OpenEMS come only from the GetSchedule row shape here, not from the UI code.
6. Whether Product 2 will run on hardware that can hold a 48-hour plan and a local time-series store (the OpenEMS resend design assumes an edge Timedata store) is a Product 2 decision outside this note.
