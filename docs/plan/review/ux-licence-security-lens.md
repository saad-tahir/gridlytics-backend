## A. Roles on screen, the viewer filter, and the leak routes (Parts 9.1, 9.4, 10.5, 2.8, 3.2, 8.5, UI items)

### F1 (high). The viewer filter strips keys by name, and the plan's own naming rules and tables put rupees under names the regex never matches

- **Location:** Part 10.5 line 849 ("every answer to a viewer has every key matching `price|cost|fee|wear|_rs|rupee` stripped, and `test_role_walk.py` greps for them"); Part 9.1 line 696; Part 9.7 line 752 (adopts R8 2.21 by reference); Part 3.2 lines 234 to 235 (`plans.objective_rs`, `cost_breakdown`, `plan_steps.reason_params JSON`), line 249 (`alerts.detail`); Part 4.7 line 405 (the reason vocabulary `genset_on(min load, diesel Rs/kWh)`, `mdi_cap(kW)`); Part 7.3 line 591 (plan `notes` carry the objective); UI-09 line 1057 ("the viewer sees no rupee columns").
- **Claim:** a server-side key filter plus a grep test is the viewer guarantee.
- **Defect:** the filter is keyed on six substrings, and the plan's own vocabulary escapes all six. (a) R8 2.21, which 9.7 adopts as the lint list, says "PKR only in exports and API fields": an API field named `objective_pkr`, `saving_pkr` or `mtd_pkr` matches none of `price|cost|fee|wear|_rs|rupee`; U3 5.4's plan message already carries `notes.objective_pkr`. (b) Money that is not named as money: `saving`, `objective`, `ledger`, `margin`, `voll` (rupees per kWh of lost load, Part 4.1), `rate_mdi`, `c_cyc`, `c_fuel`, `c_start`, the `rates` object inside `tariff_versions.body`, `kpis.mtd_saving`. (c) Values, not keys: `plan_steps.reason_params` is a JSON blob whose values hold "diesel Rs/kWh" for `genset_on`; `alerts.detail` holds "negative saving day: Rs -1,200"; `overrides.reason` and alert notes are free text; and the per-step reason sentence R8 2.9 wants ("ReasonChip plus one sentence") is rendered from those params. A grep for six substrings over JSON keys passes every one of these. (d) The filter runs on JSON answers only; see F3 for PDFs and CSVs.
- **Evidence:** R8 2.0 line 178 ("Implemented as a server-side field filter on the resources, not a client-side hide, so the numbers never reach the browser"); R8 2.21 line 548 ("'PKR' only in exports and API fields"); R8 2.9 line 356 ("prices as money are replaced by the window label"); Part 4.1 VoLL row; Part 4.7 line 405.
- **Replacement (10.5, last paragraph, replacing the filter sentence):** "Money is a type, not a name: every rupee or paisa field in `schemas.py` is declared `Money` (an `Annotated[int, Unit('paisa')]` or `Annotated[float, Unit('rs_per_kwh')]`), every reason is stored as `reason_code` plus typed `reason_params` whose money members are `Money`, and the viewer serializer drops every `Money` field and every free-text field marked `MayHoldMoney` (override reasons, alert notes, detail blobs) from any answer to a role without `see_costs`; reason sentences for a viewer are rendered server-side from a viewer-safe template per code (`genset_on` reads 'Genset on: cheaper than the alternative', no figure). `test_role_walk.py` asserts (1) that no field whose name or unit mentions rupees, paisa, PKR, price, cost, fee, wear, saving, objective, rate or VoLL is untyped, by walking every response model, and (2) that a viewer's answer to every route contains no `Money` value and no digit sequence equal to a money value in the admin's answer to the same route. Field names never use `pkr`; exports carry 'PKR' in headers only."

### F2 (high). The control tier is two facts in one column, a site key can assert the highest one, and nothing binds a message's `site_id` to the key that sent it

- **Location:** Part 2.3 line 142 ("asserted by the data source ... never by the cloud"); Part 3.2 line 225 (`sites.control_tier (edge-asserted)`, one column); Part 9.4 line 738 ("The tier is changed only in site settings by the owner, and never above what the data source supports"); Part 10.5 line 839 (`change_tier`: admin); Part 2.6 line 187 and 10.5 line 849 (a site key: `telemetry:write`, `plans:read`, `sites:read`); DAT-03 line 988; UI-17 line 1096 ("the tier never rises above what the source supports"); Part 7.3 line 590 (capabilities carry "control tier (edge-asserted)").
- **Claim:** the tier is safe because the edge asserts it and the owner changes it.
- **Defect:** the plan states both rules and stores one value, so the agent must pick one. If the column is edge-asserted (2.3, 3.2, 7.3), whoever holds a site's API key (an installer's gateway, a partner, anyone who copied the key off a Raspberry Pi) posts one capabilities message with `"control_tier": "closed_loop"` and the cloud, per 2.4 step 5, signs and queues plans for that channel; the Fleet page shows "Following plan"; fidelity in tier 3 is scored from read-back (9.4 line 738; R8 2.12), which the same key fabricates in acks, so the saving that prices the fee (15.4) is written by the party being paid. If the column is admin-set (9.4, 10.5), the edge's assertion is ignored and a site can sit in closed loop with an edge that has disabled control. U3 5.3 ("control_tier is edge-asserted, never set by the cloud") and R8 2.15 ("changed in site settings ... only by the owner after the conformance check") are both right because they are two different facts: what the source can do, and what the customer allows. Separately, DAT-03 never says the envelope's `site_id` must equal the key's site: a key for site A can post telemetry, capabilities, events and acks under site B's id (site ids are global strings in U3 5.1), a cross-site write inside a company file.
- **Evidence:** U3 5.3 rules paragraph; U3 3.5; R8 2.2 Tab D ("advisory and closed loop are selectable only when the data source is an edge or an OEM cloud with write support, otherwise greyed with the reason"); R8 2.15 Tiers; Part 15.1 Cybersecurity row ("OEM cloud credentials are a known incident class").
- **Replacement (3.2 `sites` row, and a new sentence in 2.3):** "`sites` carries `tier_allowed` (set only through `change_tier`, default monitor, never above `tier_capable`) and `tier_capable` (the latest source assertion: the edge's capabilities, or 'advisory' for CSV and OEM-cloud sources, or 'monitor' until a source reports); the effective tier is the lower of the two and is the only value the UI shows and the scheduler reads. A source assertion can lower the effective tier at once (and raises a Control alert); it can never raise it. A capabilities message asserting a higher tier than `tier_allowed` is stored, flagged and ignored." In DAT-03's acceptance: "every edge message is refused with 403 and audited when its envelope `site_id` differs from the key's site; a key for site A posting as site B is a contract test (suite 2)." In 10.5: "two key kinds: a site key (one site; `telemetry:write`, `plans:read`) issued on UI-06, and an integrator key (all the company's sites, `telemetry:write` only) issued on UI-18; a plan message served to a key carries no `Money` (no `notes.objective_pkr`), since partner gateways are not the customer."

- **Location:** Part 14.3 rule 4 line 1222 (the allow-list: "MIT, BSD, Apache-2.0, ISC, PSF, EPL-or-BSD dual-licensed packages taken under BSD, MPL-2.0 unmodified in bench only, LGPL in verification only"); Part 10.7 line 859; Part 10.9 line 867 (`licences` = pip-licenses, backend only); Part 11.5 line 927 (no npm licence step); Part 14.3 rule 2 (notices file in the backend only); Part 11.2 lines 902 to 903 (web `docs/` has no notices file); Part 14.1 line 1198.

- **Defect:** (a) the runtime graph is not inside the list. `httpx` and `requests` (pvlib) pull `certifi`, which is MPL-2.0: the rule allows MPL "in bench only", so the job fails on the API's own install, or the agent widens the list ad hoc on day one. `matplotlib` pulls `pillow`, whose metadata licence is HPND (the historical permission notice), not on the list. ## C. Keys, parsers and the control-action roles (Parts 2.8, 7.3, 7.5, 10.3, 10.5, FOR-08, TAR-09, UI-15)

### F9 (medium). Plan signing keys have no provisioning, rotation, storage or backup rule, and the tables cannot say which key signed a plan

- **Location:** Part 2.8 line 204 ("Plans signed with Ed25519 per site; the key in the data folder's secrets, rotated on handover; the edge rejects unsigned, replayed or foreign-site plans"); Part 10.3 line 814 (`_PLAN_SIGNING_KEY_DIR`, no default, no permissions); Part 3.2 line 237 (`plan_messages`: `message JSON, signature, sent_at`, no `key_id`); Part 7.3 line 594 (commands: release, hold, request_capabilities, request_debug_window, request_native_capture; no key rollover); DLV-03 line 1087; Part 2.7 Secrets and Data rows (lines 195 to 196); DEP-07 line 1110 (the three backup layers copy SQLite files and `/data/backup/`, `/data/archive/`).
- **Claim:** signing is settled by naming the algorithm and a directory.
- **Defect:** U3 5.1's envelope carries `key_id` and U3 3.3 says the cloud "rotates per site keys on handover", which needs four things the plan never writes: how an edge learns a site's public key at enrolment, how a rotation reaches the edge (there is no `rotate_key` command and a plan signed by an unknown key answers SIG_INVALID), where the private keys live (if under `data/`, the daily SQLite copy skips them, so a host loss means re-enrolling every edge by hand; if under `data/backup/`, they go off-machine in clear), and which key signed a stored message (`plan_messages` has no `key_id`, so a dispute two rotations later cannot re-verify a signature). ## Verdict

Parts 9 and 11 condense R8 and U1 faithfully in shape (the page list, the lettered-tab rules, the polling cadences, the design rules and the lift of the sign-in pages all match their sources), and the re-assembled 10.5 and 11.3 remove the two worst earlier gaps.
